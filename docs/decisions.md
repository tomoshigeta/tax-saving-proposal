# 設計判断の記録

仕様書v1をブラッシュアップする過程で確定した判断と、その理由。
「なぜこうなっていないのか」を後から辿れるようにするための記録。

## 前提となる方針

**簡易計算を優先する。** 厳密さより、入力項目が少なく数字がすぐ出ることを取る。
この方針が、以下の複数の判断の根拠になっている。

---

## D1. v1ではAIによる図面読み取りを行わない

v1ドラフトには「サーバー側DBは不要」と「Claude APIによる図面解析」が併記されていたが、
この2つは両立しない。ブラウザから直接APIを叩けばAPIキーが露出する。

抽出対象は「間取り図・外観写真・住所」のみで、画像はどのページを使うか人間が選ぶ必要があり、
住所は1行の入力。AIが節約する時間に対して、APIキー管理・課金・抽出失敗時のフォールバックUIの
コストが見合わない。

**判断**: v1では手動アップロード + 住所手入力。将来AI抽出を入れる場合は、薄いサーバー
(Vercel/Cloudflare Functions等)をAI呼び出しのためだけに置く。

## D2. 出口(売却時)の課税は提案書に記載しない

減価償却による節税の多くは繰り延べであり、簿価が下がる分だけ売却時の譲渡所得が増える。
「定年までの節税効果合計」をヒーロー数値に置くと、実質の手残りより大きい数字が最も目立つ
位置に来る、という点は検討したうえで、**現行どおり節税額のみを表示すると決定した。**

将来、出口シミュレーション(想定売却価格 → 譲渡所得税 → 通算後の実質手残り)を追加する
余地は残す。

## D3. 累進税率を計算せず、所得税率を選択式にする

当初は「想定年収 → 給与所得控除・基礎控除 → 累進表 → 所得税」という積み上げを検討したが、
**提案時点で顧客の課税所得が分からないことが多い**ため採用しない。

「通算前の税額 − 通算後の税額」の差分方式も同じ理由で不採用。

**判断**: 所得税率を 33% / 40% / 45% から選択 + 住民税10%固定。この3つ以外の税率帯の顧客は
このアプリの想定対象外。復興特別所得税(所得税額×2.1%)は簡易方針に沿って考慮しない。

**副次的な決定**: 想定年収は計算に使わないため、入力項目からも提案書の表示項目からも削除する。
年収と手選択の税率を並べて表示すると「年収からこの税率を導いた」と誤読されるため。
代わりに右上に適用税率を表示する。

## D4. 土地に対応する負債利子を損益通算から除外する

租税特別措置法41条の4により、不動産所得の赤字のうち土地取得のための借入金利子に相当する
部分は損益通算できない。これを無視すると節税額が過大に出る。

区分方法は2通りあり、**建物優先充当**(措置法施行令26条の6第2項)を採用した。
負債はまず建物の対価に充てられ、次に土地に充てられたものとして計算できる、という
納税者有利の取扱いである。

価格比按分と比べた差は自己資金が厚いほど大きい。物件価格3,000万(建物1,000/土地2,000)・
自己資金2,000万・借入1,000万のケースでは、価格比按分だと土地対応借入667万だが、
建物優先充当だと0円になり、損益通算の除外自体が消える。

なお建物優先充当に用いる建物価格は**契約上の対価**とし、仲介手数料を加算しない
(条文が「建物等の取得の対価の額」と定めているため)。

## D5. 仲介手数料は経費ではなく取得価額に算入する

国税庁の質疑応答事例により、賃貸用の土地建物を購入した際の仲介手数料は必要経費にならない。
土地分は土地の取得価額、建物分は建物の取得価額に算入され、建物分のみ減価償却を通じて
期間配分される。

当初「初年度諸費用として物件価格の7%を経費計上」という案を検討したが、これは誤りだった。

**判断**:
- 諸費用の入力は**仲介手数料**と**ローン事務手数料**の2つのみ
- 仲介手数料の建物分 `F × B / P` を減価償却の基礎に加算する
- ローン事務手数料は初年度の必要経費として計上する

**この判断から導かれる実装上の原則**: 税務上の経費と現金支出を別概念として型で分ける。
仲介手数料は「現金支出だが経費ではない」、減価償却費は「経費だが現金支出ではない」。
1つの `expense` にまとめると必ずバグが入る。

## D6. 空室率・家賃下落を考慮しない(家賃保証前提)

サブリース(家賃保証)を前提とするため、空室率と家賃下落率は入力しない。

ただしサブリース契約は通常、期間ごとの賃料改定条項を持ち、保証賃料は契約期間を通じて
固定ではない。全期間フラットのグラフを出す以上、この前提は書面に明示する必要がある。

**判断**: 計算モデルはフラットのまま。提案書の脚注に
「保証賃料は契約に定める期間ごとの改定対象であり、本試算は現行の保証賃料が継続する前提です。」
を1行入れる。

サブリースの免責期間(新築時の当初1〜3ヶ月)は簡易方針に沿ってv1では扱わない。

## D7. 償却終了後の増税年はグラフに表示しない

減価償却が終わると不動産所得は黒字に転じ、税金は増える。グラフ1(年間節税額の推移)では
その年の棒がマイナスになる。

そのまま下向きに描く案も検討したが、**0でクリップして描かない**ことにした。
節税効果合計にも算入しない。

## D8. 設備分離はRC造のみ

建物本体と建物附属設備(電気設備・給排水衛生設備・ガス設備、いずれも15年)を分けて償却すると
初期の償却費が増える。中古設備に簡便法を適用すると、築15年超のRC造では設備の耐用年数が
`15 × 20% = 3年` となり、初期3年の償却費が大きく増える。

区分マンションの売買契約書には建物価格しか出ないことが多く按分根拠は弱いが、
**v1では否認リスクを考慮せず、手入力で分離できるようにする。**

木造・木骨モルタル造の建物附属設備は建物本体と一括して建物の耐用年数を適用できるとされており、
分離の根拠が特に薄い。v1をシンプルに保つため、**設備分離はRC造のみに限定**し、
それ以外の構造では設備価格の入力欄を無効化する。SRC造も v1 では対象外。

設備価格は建物価格の**内数**として入力する(売買契約書に出るのが「建物価格」であり、
そこから設備分を切り出すのが実際の作業手順であるため)。

## D9. 借入額は物件価格 − 自己資金

借入額を直接入力する案(金融機関が承認した実額を表現できる)も検討したが、
入力を減らす方針を取り、`借入額 = 物件価格 − 自己資金` とした。

諸費用(仲介手数料・ローン事務手数料)はローンに組み込まず、自己資金とは別に手元から
支出するものとして扱う。したがって手元からの初期支出は `自己資金 + 仲介手数料 + ローン事務手数料`。

## D10. 初年度の減価償却を月割しない

取得月によって初年度の償却費は本来月割になるが、月割にすると取得月の入力が1つ増え、
「いつ買うか」で提案書の数字が動いて比較検討の道具として使いにくくなる。

**判断**: 初年度も満1年分を計上する。

## D11. IndexedDB + JSONエクスポート

localStorage は約5MBかつ文字列のみで、画像をbase64化すると約1.33倍に膨らむため、
間取り図と外観写真を数件保存した時点で破綻する。**IndexedDBで確定**(選択の余地がない)。

ブラウザのキャッシュクリアやPC買い替えで履歴が全消滅するため、
**JSONエクスポート/インポート**を備える。

顧客名は任意入力とし、空欄時は一覧で「物件名 + 作成日」を表示する。

## D12. React + TypeScript + Vite、静的ホスティングに公開

年次テーブル・2つのグラフ・3画面・履歴管理があり、素のJavaScriptでは状態管理が保たない。

TypeScriptを採用する理由はこの案件固有で、**月額/年額・率/パーセント・年/月の取り違えを
型で止められる**こと。実際、v1の月々CF計算式には単位の不整合があった。

データは各利用者のブラウザ内にあるため、静的公開しても他人からは見えない。
公開する方がタブレット利用とPC買い替えの両方にそのまま対応できる。
